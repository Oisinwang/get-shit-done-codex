# 比較ガイド

GSD Codex をリポジトリに追加する価値があるか、それとももっと軽いワークフローで十分かを判断するときに、このページを使ってください。

## 短い結論

GSD Codex は、長時間の AI コーディングセッションで持続的なプロジェクト記憶、段階的な計画、検証、再開サポートが必要な作業に向いています。Codex そのものの代替ではありません。汎用の task manager や CI システムの代替でもありません。

## 適合度を比較する

| 選択肢 | 最適な場面 | GSD Codex が埋める主なギャップ |
|--------|------------|--------------------------------|
| 生の Codex chat | 小さく明確な編集があり、1 回のセッションで検証まで終えられる | コンテキストリセット後も目標、意思決定、計画、検証を残す |
| prompt pack | よくあるコーディング作業の文言を再利用したい | prompt を、プロジェクトファイル、フェーズ成果物、復旧メモを持つ状態ありのワークフローに変える |
| task manager | 人間が backlog の所有者、担当、スケジュールを管理する必要がある | `AGENTS.md`、`.codex/`、`.planning/` の下に、coding agent が実行できるプロジェクトコンテキストを置く |
| CI-only workflow | テストが受け入れ条件の全体をすでに定義している | テストがすべてを覆う前に、要件、リスク、設計判断、手動 UAT を記録する |
| 完全なエンタープライズプロセス | 大規模チームが正式な承認やプログラム管理を必要としている | 個人や小規模チームの AI 作業を、重いプロセスなしで構造化する |

## GSD Codex を選ぶ場面

- 機能が大きすぎる、またはリスクが高すぎて、1 つの prompt では終わらない。
- コンテキスト圧縮や新しいセッションの後も、Codex に作業を再開してほしい。
- 要件を書き残さないと、途中でずれやすい。
- 複数のファイル、コマンド、agents、workstreams を調整する必要がある。
- 検証にテスト、手動チェック、セキュリティメモ、UAT 証拠を含めたい。
- git でレビューできる計画成果物がほしい。

## GSD Codex を使わない場面

- タスクが 1 行の編集で、必要な patch がすでに明確である。
- `.planning/PROJECT.md`、`.planning/ROADMAP.md`、`.planning/STATE.md` のような計画ファイルを置きたくない。
- レビュー可能な意思決定や検証記録なしで、agent に直接変更させたい。
- チームにすでに強いプロジェクトワークフローがあり、必要なのは少数の再利用 prompt だけである。

## 実際に追加されるもの

Codex-first インストールでは、ローカルインストールなら `.codex/`、グローバルインストールなら `~/.codex/` に commands と skills が追加されます。プロジェクト内では、GSD が通常の Markdown と JSON の計画成果物を `.planning/` に書き込みます。これらの成果物は確認しやすく、git に載せやすく、リポジトリ方針でローカル計画状態を保持しない場合には取り除けるように設計されています。

中心となる契約は次の通りです。

- `AGENTS.md` はプロジェクト指示を保存します
- `.codex/` は Codex-native command と skill surface を提供します
- `.planning/` は持続的なプロジェクト状態を保存します
- `$gsd-*` コマンドはワークフロー入口になります

## 実用的な判断基準

すばやい編集には生の Codex を使います。コンテキストを失う、計画を飛ばす、検証を忘れるコストが、ワークフロー状態を書き残すコストより高いなら、GSD Codex を使ってください。
