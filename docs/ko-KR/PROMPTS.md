# 프롬프트 레시피

GSD Codex를 설치한 뒤 아래 내용을 Codex에 붙여넣으세요. 이것들은 셸 스크립트가 아니라 프롬프트입니다. 각 프롬프트는 Codex에게 어떤 GSD 경로를 사용할지, 어떤 상태를 확인할지, 어떤 증거를 남길지 알려 줍니다.

프롬프트를 실행하기 전에 대괄호로 표시된 자리표시자를 바꾸세요.

## 새 프로젝트 시작

아직 지속 가능한 프로젝트 상태가 없고 아이디어만 있을 때 사용하세요.

```text
[목표]를 만들고 싶습니다. GSD Codex를 사용해 이 아이디어를 지속 가능한 프로젝트 상태로 바꿔 주세요.

`$gsd-new-project --auto`를 실행하고, 생성된 `.planning/PROJECT.md`, `.planning/ROADMAP.md`, `.planning/STATE.md`를 검토한 뒤 `$gsd-next`로 계속 진행하세요.

첫 번째 phase는 작게 유지하세요. 검증을 건너뛰지 마세요. 작업이 완료되었다고 말하기 전에 검증 증거와 변경된 파일을 보여 주세요.
```

## 기존 저장소

이미 코드, 테스트, README가 있는 저장소에서 새 작업을 계획하기 전에 사용하세요.

```text
이 기존 저장소에서 새 작업을 계획하기 전에 GSD Codex로 코드베이스를 먼저 이해하세요.

`$gsd-map-codebase`를 실행한 뒤 `$gsd-new-project --auto`, `$gsd-discuss-phase 1`을 차례로 실행하세요. 구현 작업을 제안하기 전에 발견한 관례를 사용하세요.

기존 사용자 변경사항을 보존하세요. `.planning/` 상태를 읽기 쉽게 유지하고, 커밋 전에 검증 증거를 보여 주세요.
```

## 작은 수정

작업 범위는 좁게 유지하면서도 추적 가능한 검증이 필요할 때 사용하세요.

```text
GSD Codex를 사용해 좁은 범위의 수정을 진행하세요: [구체적인 버그 또는 작은 개선].

`$gsd-fast "[구체적인 버그 또는 작은 개선]"`를 실행하세요. 변경을 집중적으로 유지하고, 가장 작은 유용한 테스트를 추가하거나 업데이트하며, 검증을 건너뛰지 마세요.

수정 후에는 동작 변경, 테스트 증거, 남은 위험을 요약하세요.
```

## 작업 재개

휴식, 컨텍스트 압축, 다른 세션의 인계 뒤에 사용하세요.

```text
GSD Codex로 현재 프로젝트를 재개하세요.

`$gsd-resume-work`를 실행한 뒤 `$gsd-progress --forensic`을 실행하세요. 다음 작업을 제안하기 전에 `.planning/STATE.md`와 활성 phase 산출물을 읽으세요.

채팅 기억으로 계획을 다시 만들지 마세요. 저장된 프로젝트 상태에서 계속 진행하고, 내 입력이 필요한 blocker가 있으면 명확히 알려 주세요.
```

## 감사 및 수정

미리 정한 작업 없이 Codex가 유지보수성 또는 release-readiness 문제를 찾아 고치게 하고 싶을 때 사용하세요.

```text
GSD Codex를 사용해 이 저장소에서 설치, 문서, 테스트, 릴리스 안전성, 첫 사용자 경험을 해치는 실용적인 문제를 감사하세요.

`$gsd-audit-fix`를 실행하세요. 문제를 영향도별로 분류하고, 확신이 높은 항목만 수정하며, 더 위험한 아이디어는 강제로 변경하지 말고 메모나 issue로 남기세요.

각 수정마다 patch를 작게 유지하고, `.planning/` 증거를 보존하며, 검증을 건너뛰지 마세요. 결과를 증명한 명령도 보여 주세요.
```

## 레시피 선택

| 상황 | 시작점 |
|------|--------|
| 새 아이디어 또는 제품 목표 | 새 프로젝트 시작 |
| 기존 코드베이스를 먼저 이해해야 함 | 기존 저장소 |
| 집중된 버그 또는 문서 수정 | 작은 수정 |
| 이전 GSD 작업이 있음 | 작업 재개 |
| 아직 작업이 정해지지 않음 | 감사 및 수정 |
